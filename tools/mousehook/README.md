# Gears of War: Judgment — мышь на русской версии (TU0)

Инструменты и инструкция для адаптации mousehook под неанглийские версии
Gears of War: Judgment. Тот же подход, что использовался для Gears of War 3.

Файлы:

| файл | что делает |
| --- | --- |
| `judgment_find_chain.lua` | ищет языко-независимые цепочки указателей на камеру. Запускать на **английской** TU0 |
| `judgment_verify_chain.lua` | проверяет одну цепочку на **русской** версии |
| `judgment_verify_batch.lua` | проверяет сразу несколько цепочек на русской версии (рекомендуется) |

Оба скрипта — для Cheat Engine, подключённого к процессу Xenia
(гостевая память доступна по смещению `0x100000000`, как в скриптах для GoW3).

## Почему мышь не работает на русской версии

Хук пишет углы камеры по адресу `cam + 0x62/+0x66`, где `cam` — указатель на
объект камеры, взятый из слота `0x448F2840`:

```
cam = [0x448F2840]        ; English TU0
cam_ru = [0x448F2840]     ; русская версия — мусор
```

`0x448F2840` — это адрес **в куче** (`0x40000000–0x50000000`). На чистой
английской сборке раскладка кучи детерминирована, поэтому адрес работает.
Как только добавляются файлы локализации (`Xbox360TOC_RUS.txt`, папка `RUS`,
`Startup_LOC_RUS.xxx`, `GearGame_LOC_RUS.xxx`, `Coalesced_RUS.bin`), меняется
порядок и размеры аллокаций — и `0x448F2840` начинает указывать на другой
объект. Именно поэтому после добавления русских файлов мышь отвалилась даже на
английском языке внутри игры.

При этом **`default.xex` у английской и русской версии одинаковый** (сравни
`Module Hash` в логе загрузки — должно быть `8429D0AE190C10DB`), значит все
адреса внутри образа (`0x82000000–0x836B0000`) общие. Вся задача — заменить
«кучезависимый» адрес слота камеры на цепочку от статического адреса:

```
root (статический, внутри default.xex) -> ... -> слот с указателем на камеру
```

искать её надо на английской версии (там известно, где камера), а применять
на любой.

## Шаг 0. Убедиться, что xex действительно одинаковый

В логе Xenia найти строку

```
i> 0000131C Module \Device\Cdrom0\default.xex:
Module Hash: 8429D0AE190C10DB
```

Хеш русской версии должен совпадать с английской. Если отличается — подход
меняется (нужно искать адреса уже для русского xex), сначала разберись с этим.

## Шаг 1. Найти цепочку (английская TU0, в геймплее)

1. Запустить английскую Judgment TU0, зайти в игру (не меню).
2. Подключить Cheat Engine к процессу Xenia.
3. Загрузить и выполнить `judgment_find_chain.lua`.
   CE будет выглядеть зависшим 1–3 минуты — это норма, идёт просмотр кучи.
4. В консоли Lua появятся строки:

```
=== НАЙДЕНО ЦЕПОЧЕК: 3 ===
root=8358ABEC  chain: {0x4A0, 0x0, 0x40}
    [8358ABEC]=41234500 [412349A0]=41345600 [41345600]=41456700 -> slot 41456740 (cam=41567800)
...
Готовые строки для supported_builds в GearsOfWars.cc:
  gengine_address = 0x8358ABEC, chain_offset_1 = 0x4A0, chain_offset_2 = 0x0, chain_offset_3 = 0x40
```

Что брать: цепочку, у которой `root` лежит внутри образа `default.xex`
(`0x82000000–0x836B0000`) и промежуточные объекты выглядят осмысленно
(не «случайный» указатель из середины какого-то объекта). Подойдёт и цепочка
короче 3 хопов — в выводе она дополняется `0xFFFFFFFF` (`-`), это sentinel
«цепочка закончилась», он поддерживается в `ResolvePointerChain`.

Варианты с одинаковым путём схлопываются отдельно для каждого статического
`root`: разные globals могут вести к одному объекту на английской версии, но
указывать на разные объекты на русской. Поэтому root не теряется при
дедупликации. Кандидаты из диапазона `0x83400000–0x83480000` выводятся первыми
как эвристика (в GoW3 GEngine root находился там; это не гарантия для Judgment).
Известный слот `0x448F2840` разбирается первым.

Если скрипт ничего не нашёл — увеличить `O1_MAX`/`O2_MAX`/`O3_MAX` в начале
файла, либо использовать Pointer Scanner (см. ниже).

## Шаг 2. Проверить цепочки на русской версии

Перебирать все найденные цепочки по одной не нужно: поисковик схлопывает
дубликаты (цепочки, идущие через одни и те же объекты, остаются в одном
экземпляре), а `judgment_verify_batch.lua` проверяет сразу пачку кандидатов
за один запуск.

1. Запустить русскую Judgment TU0, зайти в игру.
2. Вписать кандидатов в `judgment_verify_batch.lua`:

```lua
local CANDIDATES = {
  {0x83549E20, 0x588, 0x1FC, 0x3DC},
  {0x83549E38, 0x598, 0x1FC, 0x3DC},
  {0x83549E44, 0x5A8, 0x1FC, 0x3DC},
  {0x83549E20, 0x60C, 0x84, 0x3DC},
  ...
}
```

3. Выполнить скрипт. Ожидаемый результат:

```
=== диагностика старого (английского) слота ===
  [448F2840] = 0   <-- НЕ указатель на кучу        <- подтверждение диагноза
=== проверка 10 кандидатов ===
  #1  root=83549E20 {0x588, 0x1FC, 0x3DC} -> cam=4A300000 (UObject)
  #2  root=83549E38 {0x598, 0x1FC, 0x3DC} -> cam=4A300000 (UObject)
  #3  ...                              -> НЕ РАБОТАЕТ: хоп 2: [...] не указатель на кучу
=== монитор углов 40 сек ===
    пошевели мышью/правым стиком: углы меняются только у реальной камеры
  #1  cam=4A300000  X(+66) = 12345   Y(+62) = 678
  #2  cam=4A300000  X(+66) = 12345   Y(+62) = 678
```

В актуальной версии batch-скрипта сначала дождись строки `СТАРТ`, затем
вращай камеру вправо 10–15 секунд, пока скрипт продолжает работать. В итоговой
сводке смотри на счётчик `X`: у кандидата реальной камеры он должен увеличиться
во время поворота (направление вправо также должно давать согласованное
изменение `X`). Нулевые счётчики означают, что кандидат не отреагировал на
поворот; ненулевые сами по себе ещё не доказательство — сравни их с тем, что
видно в игре, и при необходимости повтори, вращая влево.

Для одиночной проверки одной цепочки есть `judgment_verify_chain.lua`
(тот же резолв + доп. диагностика fov scale и «живого» `LookRightScale`).

## Шаг 3. Вставить значения в код

В `src/xenia/hid/winkey/hookables/GearsOfWars.cc` в записи
`GearsOfWarsJudgment_TU0` заменить `NULL, NULL, NULL, NULL` на найденные
значения:

```cpp
    {GearsOfWarsGame::GameBuild::GearsOfWarsJudgment_TU0,
     {0x8358ABEA, 0x47656172, kTitleIdGearsOfWarsJudgment, 0x83551871,
      0x83552939, 0x448F2840, 0x66, 0x62, 0x41DE7054, 0x448F2840, 0x6D4, 0x154,
      0x448F2840, 0x3AC, 10000, 53535,
      0x8358ABEC, 0x4A0, 0x0, 0x40}},   // <-- gengine_address + chain
```

Как это работает в коде:

* `GetCameraPointerAddress()` резолвит цепочку вместо использования
  `camera_base_address` (`0x448F2840`);
* `FOVScale()` автоматически берёт fov от того же объекта камеры;
* патч «живого» `LookRightScale` тоже идёт через объект камеры
  (`[cam + 0x6D4] + 0x154`) вместо невалидного на русской версии
  `LookRightScale_live_address`;
* запись по старому статическому `LookRightScale_address` теперь защищена
  проверкой «похоже на чувствительность», чтобы не писать `0.05f` в случайное
  место.

Для TU4 процедута та же, но `CAM_SLOT = 0x42943440` и `IMG_STOP` берётся из
её лога загрузки (`Load Address + Image Size`).

## Отладка

Собранный с `--gears_debug` эмулятор пишет в лог:

* какой билд определён (`detected build N`);
* почему хук не работает: `camera slot 448F2840 holds XXXXXXXX, expected a
  heap pointer`.

## Если скрипт не справился: Pointer Scanner в CE

1. На английской TU0 в геймплее добавить адрес `0x448F2840` вручную,
   прочитать значение — это `cam` (указатель на объект камеры).
2. Выделить адрес `cam` → *Pointer scan for this address*.
3. В окне скана: максимальный уровень 3–4, смещения до `4095`, включить
   *Only find paths with a static base address*, диапазон адресов ограничить
   `0x82000000–0x836B0000` (образ `default.xex`).
4. Дождаться pointermap и результатов, отфильтровать невалидные пути
   (rescan).
5. Взять короткий путь вида `0x8358xxxx → +0x4A0 → +0x0 → +0x40` и вставить
   как `gengine_address` + `chain_offset_1..3`.
